# Canonical Visual Identity and Image-Generation Context Audit

## Scope

This Phase 12 maintenance audit records the owner-authorized repair for canonical visual continuity during image generation and other representation handoffs. It adds no campaign data, image asset, release claim, numbered Future Revision, or new gameplay phase.

## Observed Weakness

Historical appearance could exist only in narration, summaries, or model context without a dedicated sparse campaign owner. A later image request could therefore produce a fluent but inconsistent depiction, copy current equipment into identity, reveal protected information, or convert a renderer's necessary guesses into apparent Canon.

The repository already required authoritative reads and one owner per mutable fact. The missing pieces were a visual-specific owner boundary and a purpose-specific representation projection.

## Repair

The maintenance adds:

- [Visual Identity](../../docs/persistence/VISUAL_IDENTITY.md) as the sparse optional owner for established identity-bearing appearance;
- [Canonical Visual Context](../../docs/ai/CANONICAL_VISUAL_CONTEXT.md) as a Derived FR-011 projection and representation-tool handoff;
- blank [Visual Identity](../../templates/VISUAL_IDENTITY_TEMPLATE.md) and [Canonical Visual Context](../../templates/CANONICAL_VISUAL_CONTEXT_TEMPLATE.md) templates;
- owner-map, Campaign State, Autonomous Registry, Life Archive, migration, validation, AI workflow, execution-profile, navigation, and template-coverage integration.

No populated schema migration is supplied. Existing campaigns add Visual Identity records only when facts are already established, recovered with provenance, or explicitly adopted.

## Ownership Result

Visual Identity does not become a monolithic appearance save. Species and form own shared embodiment architecture. Models own shared design traits. Individuals own established identity-bearing divergences. Inventory owns equipment and custody. Condition owners retain injuries and temporary effects. Locations and the World Engine own environment and place facts.

Current Appearance assembles those owners for one time and request. Canonical Visual Context filters that assembly for one Perspective and tool handoff. Both are non-authoritative Derived Data.

## Historical Recovery

Historical visual recovery is targeted rather than exhaustive. The operator identifies the subject, Life or interval, and missing trait; searches likely canonical sources; preserves exact provenance, uncertainty, effective interval, and conflicts; and writes only recovered facts justified by those sources. Missing evidence remains unspecified.

Former bodily appearance remains historical after Reincarnation. It does not automatically become the new body's appearance.

## Representation and Adoption

Canonical image generation normally has `Affected Set = empty`. The tool receives established facts, unknowns, secret exclusions, and non-canonical rendering freedom. Its output is presentation, not evidence.

An authorized player or GM may explicitly adopt a rendered trait. Adoption becomes a separate state-changing interaction routed to the Visual Identity or other proper owner and must satisfy FR-011 persistence and validation before the trait is durable.

## Regression Coverage

The Canonical Visual Context contract defines and the repository validator checks cases for:

- an established recurring character;
- an unspecified eye colour;
- current equipment;
- an autonomous servitor Model;
- Evolution;
- Reincarnation;
- an unidentified structure;
- a GM Secret;
- conversation conflict with persistence;
- explicit approved image-trait adoption;
- an unapproved generated trait.

## Validation

The repository validator passed after integration. It checked 247 Markdown files, 6,850 relative links, 154 anchors, 167 canonical documents, 13 documentation-family indexes, 42 templates, 1,198 terminology headings, and 186 roadmap tasks. It also confirmed Visual Identity invariants, all eleven Canonical Visual Context regression headings, index and registry coverage, template coverage, terminology uniqueness, roadmap state, zero orphaned Markdown documents, and zero forbidden campaign-data directories.

The existing FR-011 executable persistence-gate harness also passed all 13 assertions. No populated campaign record, generated image, credential, private locator, schema migration, or external-host claim was added.

## Runtime Boundary

The repository can require and structurally validate the representation contract, but it cannot force an external image-generation host to perform campaign reads or obey the supplied packet. A conforming runtime must prove that it loaded current canonical sources and must not claim canonical fidelity when the required data or tool access was unavailable.
