## Adoption Operation Reconstructed

Distinguish two scopes before assigning work:

1. **FR-011 operational adoption:** back up the existing canonical save; validate its active version/owner graph; preserve working read queries; configure/regenerate Derived caches without rewriting Canon; enable automatic turn transactions; verify adapter/validation/read-back; exercise read/write/rollback/reload on a harmless isolated fixture; record provenance and activate only after validation. Most work is host conformance, not fictional adjudication.
2. **Material Repository/model/campaign conversion:** if the proposed setup changes adopted rules, logical representation or established claims, use Backup -> Audit -> Merge -> Validation, with compatibility adjudication/retcons when needed. A new rules import/publication is input availability, not campaign adoption. A moving RC label is resolved to immutable identity, never used as the campaign's sole revision pin.

For either scope: authorized request -> resolve existing campaign/authority and exact source/target identities -> complete protected recovery copy -> read-only evidence audit -> bounded compatibility decisions and any continuity cases -> authorized Merge Plan -> isolated candidate -> complete required validation -> atomic active-version selection and verified read-back -> truthful acknowledgment/readiness. Acquisition, player consultation and source recovery are prerequisites or branches inside that flow, not extra fictional turns.

No new campaign is created to evade missing configuration. Unavailable Canon remains unavailable. A conversation can locate testimony but cannot become the replacement save. An already compatible FR-011 setup may need no GM decision and no fictional change; it still needs genuine technical evidence. A host cannot claim conformance because these documents or a parser pass.

## Simultaneous Context and Host Boundary

For D05, old claim + new rule + proposed mapping + exact relevant owner evidence must coexist. For D07, both claims and all distinctions needed to classify their apparent disagreement must coexist. For D08/D09, the complete connected impact/reliance group, proposed alternatives and their materially different consequences must coexist. A choice cannot be made against a summary that drops a protected distinction or unresolved branch. D16 compares source, candidate and approved change together. D21 receives verified completion state and only the audience-authorized explanatory consequences.

Authority is complete local executable rules; campaign evidence is exact scoped state/history; prior results are reloadable versioned findings/approvals, not substitute rules; explanatory examples are optional unless they contain a unique operative qualification. A model never substitutes an approved earlier answer for the rules needed to interpret a new decision. The semantic maximum is **variable with the material conflict group and its specialist owners**, not universally 14,536 or a fixed number of campaign records. Some groups cannot be safely decomposed.

Host delegation has explicit bases: runtime layers assign fetch/write/verify to implementations; Stage 1 assigns immutable copy/integrity; Audit and Validation permit indexed structural checks; Save/Managed assign parent checks/idempotency/atomic activation/read-back; Host Bootstrap assigns presented/confirmed status without calling user confirmation technical proof. These gates can execute without the model rereading the complete turn state machine, cache implementation, transaction writer, schema guidance and regression catalogue on every administrative comparison. Their code must actually enforce the contract, rather than assume a prior model read it.

Context relevance and semantic ownership are not automatically deterministic. H can follow typed references and detect stale IDs; M must request missing material evidence and determine whether apparently separate claims interact. Host closure is necessary but not sufficient for semantic closure. If that inference needs unavailable evidence/rules, the ticket stops.

The eight FR-011 adoption duties have explicit owners: steps 1-2 D03/D15; step 3 D04/D13 plus D05 for semantic query assumptions; steps 4-6 D13/D15; step 7 D15 isolated fixture; step 8 D18-D22. No C responsibility is waived: ordinary turn rules remain with the gameplay consumer, host I/O/conformance gates remain with H, and model interpretation remains with the relevant ticket. An administrative ticket is not `gameplay.resolve`; an actual gameplay test that uses that operation still gets the mandatory Kernel and GM Procedure, including its 2,027 floor.

## Canon Atomicity and Acknowledgment

Reasoning may take many invocations. **Canonical activation may not expose half a conversion.** Before activation, all active adjudication still uses the old validated Campaign Version/profile. Candidate records and process-history updates are durable but not active fictional claims. The final storage-equivalent atomic switch selects the target, adopted Repository/model/profile metadata and Save Index consistently. A separately published global Rule Store artifact does not adopt it for a campaign.

Immediately before that switch, compare the source parent against the current active state and verify unchanged plan/approval/validation inputs. A concurrent gameplay save cannot be overwritten. Either pause dependent work at the valid boundary or re-audit/rebase through authorized migration; do not treat an unrelated newer timestamp as approval. All required owner writes and ancestry must be staged coherently before the active pointer changes. Restore/read-back and configured canonical deployment are part of completion, not intentions.

The constrained set-only patch cannot perform structural creates/deletes, identity merges or profile migration as a loophole. Stage 3 uses the migration's appropriate owner operations. FR-011's no-background-gameplay-save rule is untouched: phased **administrative candidate reasoning** is not permission to narrate persistent gameplay consequences before commit.

Lost acknowledgment has three branches: durable committed+validated -> report the same result, no replay; durably incomplete -> resume earliest incomplete safe stage with the same applicable transaction identity; unknown/unreachable -> pending or failure and recovery, never assume commit or absence. FR-017 already establishes this behavior; FR-030 still owns the lightweight query/compact acknowledgment implementation. Activation success followed by failed delivery leaves the new version committed, not silently rolled back. Rollback is authorized recovery with ancestry and later-gameplay impact review, never deletion of history or reuse of a cancelled/failed Migration ID.

## Conflicts, Visibility and Campaign Scale

A specialist case can run within Audit, or be re-entered when Merge/Validation reveals a new issue. The canonical smallest sufficient conflict closure and narrow Freeze disprove a universal requirement to view every campaign conflict simultaneously. Independence must be **demonstrated**, not assumed from different names or array rows.

Group interacting read/write owners, references, causal/temporal constraints and Reliance Effects. A remedy for one claim may invalidate another baseline, participant approval, plan operation or validation result; link and re-open those dependents before activation. Model-discovered semantic links expand the group and invalidate its old closure certificate. A connected group whose outcome cannot be decided independently remains one simultaneous decision; it is not split to meet a budget. Retcons require genuine campaign authority and consultation of materially affected participants, not a repository update, a model preference or silence. Deception still requires actor/opportunity/method/intent/causal evidence.

Secrets can be present in every protected storage stage and M ticket when material and authorized. Host comparisons, indexes and worklist counts must not reveal hidden IDs, titles, findings or backlinks through public metadata. Participant consultation receives enough authorized consequences for consent without copying the private case. If meaningful consent cannot be obtained under the access agreement, adoption remains blocked rather than misrepresenting informed approval. Technical receipts carry safe identity/status, not secret evidence. M explanation is checked against the disclosure route; correcting world truth does not automatically grant Character Knowledge.

Large campaigns do not imply loading all Canon into one prompt. Structured persistence permits module partitions/indexes and typed material dependency closure; Repository Upgrade audits materially affected claims, not a wholesale reinterpretation of every life. Deterministic storage scans may inspect all required records over many batches without injecting them into M. Each M ticket still needs all material evidence, not a lossy recap. FR-028 is the planned executable active-Canon closure mechanism; a bulk adoption worklist can use those ownership/closure principles, but that service is not implemented yet.

## Boundedness and Termination

The stage types are fixed by Canon: four plus request/activation boundaries. For a pinned source/target, enumerate a finite authorized worklist of source records, differences, findings and required validation checks. Each ticket names a stable owner/claim/group and the exact input/plan revision. Processing, dependency expansion and protected storage batching are bounded by that finite scope, not campaign age in the prompt.

Each item ends resolved+authorized, unchanged, explicitly deferred under a permitted non-blocking disposition, rejected/abandoned, or unresolved/blocked. Unavailable authority, an over-budget indivisible group or missing source cannot disappear from the list. Activation requires complete required coverage, no unresolved Blocker/Error, every Warning disposition and successful final baseline verification. Counting completed batches without checking global relationships is insufficient.

New semantic links enlarge/invalidate the appropriate connected group; new source scope/version requires a recorded revised audit boundary and authority, not an endlessly growing queue against a moving baseline. Use a deployment-declared finite retry/review limit per exact input revision; Canon does not provide a universal numeric value. Retry only transient/incomplete stages with verified input identity. Rejection or unchanged missing evidence is not a reason for repeated speculative model attempts. Exhaustion ends Blocked/Inconclusive or authorized abandonment. Specialist calls do not recursively ask arbitrary further specialists: host owns the finite closure/worklist, review points and affected approval invalidation.
